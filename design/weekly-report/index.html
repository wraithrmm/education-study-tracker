Education Tracker · design concept

The ledger and the margin

Every number on the weekly report is computed by the tracker from the record it already holds, on every request — that is the ledger, and it changes the moment Dad excuses a block. What Claude adds on Friday is judgement: what held, what slipped, one carry-forward line per subject, next week's plan — stored once, dated and signed, in the margin.

What's computedStudy blocks done, short, missed, excused and extra, partitioned by tracking; hours against the timetable; topic movement; coverage; attempts, practice and queue tops. Derived on every request.
What's writtenHeld · Slipped · Next week, and one carry-forward line per subject. Stored as a dated, signed note with a snapshot of the counts it was written against.
Where it lives/week/{iso} is the page for the parent; /weeks is the term as a ledger; the Friday email is a digest with a link, not the report.
Friday, 14:05The routine reads the week in one call, writes the note as draft, emails the digest. At 14:15 the review records the decisions and saves version 2 as reviewed.

Why the split works

Dad can trust the top of the page because no model wrote it, and the bottom because it is dated and says what it was written against. Two runs of the routine can disagree about wording; not about how many blocks were missed.

The drift line

The one place the two halves touch. The draft was written at 14:05, before Dad excused Wednesday's Spanish; rather than contradicting the register, the note says what it knew. The reviewed version's snapshot matches, so the line goes quiet.

Rules kept

No streaks. Misses named with day, time, label and what was absent. No cross-subject accuracy comparison. Nothing about Paige beyond the work — the page is public. No control here excuses anything.

Why a table

The term question is comparative — is the shape getting better — and eight rows of the same eight columns answer it without a chart. The 21-segment bar is the only picture and it is the same one as on the week page.

Pre-timetable weeks

The timetable is valid_from 2026-09-07, so W34–W36 have nothing to judge. Showing “— no timetable yet” rather than “0/0” keeps the column honest when someone scrolls back in six months.

Cost to build

One page, one query per week from the same judgeWeek() the index already calls, plus the latest weekly_reviews row per week for the stamp column.

Why a digest

The record has one home. An email that carried the report would be stale the moment Dad excused Wednesday's Spanish — and there would then be two versions of the week, one of them wrong and un-fixable.

What it must carry

Enough to act on without opening anything: the headline, the misses by name, and the decision waiting on him. Everything else is a reason to tap the link.

Plain text

Monospace-ish, 60 columns, no images. Renders the same in every client and reads fine when a phone strips the formatting.

5

How it's built

The part the implementation session reads. Everything above is computed from what the tracker already stores except one table, two tools and one routine.

Schema — step 5

weekly_reviews (
  id            INTEGER PRIMARY KEY,
  week          TEXT    NOT NULL,          -- '2026-W37'
  version       INTEGER NOT NULL,          -- 1, 2, 3 …
  stage         TEXT    NOT NULL,          -- 'draft' | 'reviewed'
  written_at    TEXT    NOT NULL,          -- ISO, Europe/London
  written_by    TEXT    NOT NULL,          -- 'routine' | 'chat'
  snapshot_json TEXT    NOT NULL,          -- counts, hours, missed[], movement refs
  sections_json TEXT    NOT NULL,          -- held, slipped, next, carry_forward{}, …
  note          TEXT,
  UNIQUE (week, version)
)

Append-only. The latest version is shown; earlier ones stay readable on the page (the draft 14:05 chip). snapshot_json holds the counts, hours, missed list and movement refs as they stood when the note was written — that is what makes the drift line possible. sections_json holds held, slipped, next, carry_forward{slug: line}, rotation_next and decisions[].

Tools

  • tracker_week_report(week) — one read that returns everything the page shows: judgeWeek + per-subject changes + attempts + practice + queue tops. Counts come back partitioned by tracking — study (evidence) is the headline, with movement (self-report) and the review block beside it, never folded in. Hours are read against planned_by_subject, computed from the timetable version in force for that week — single-subject blocks only, so the mixed retrieval blocks are planned for no one subject — not against a fixed targets split. The routine makes one call instead of twelve.
  • tracker_save_weekly_review(week, sections, stage, snapshot?) — writes a new version. The server fills the snapshot itself from judgeWeek and the week's changes, so the model cannot mis-state the counts it is writing against.
  • tracker_get_weekly_review(week) — the latest version plus the list of earlier ones.

Pages

  • /week/{iso} — already planned in the dashboard skill for the timetable. Gains the by-subject section and the margin. One query per section, all computed at request time. Both the headline card and snapshot_json use the same partition and the same planned_by_subject, so the page and the note can never count differently.
  • /weeks — new. One row per week, same judgeWeek, plus the latest review row for the stamp column.
  • No page anywhere gains a control that writes to the record.

The Friday routine

  • Replaces the current Maths-dashboard prompt. Cron Friday 14:05 Europe/London — 05 13 * * 5 in UTC while BST is in force, 05 14 * * 5 after the October change. The DST shift has to be handled, not assumed away.
  • Steps: tracker_week_report → write the margin note with tracker_save_weekly_review(stage: 'draft') → email the digest with the link.
  • 14:15, in chat: the parent-weekly-review skill records the decisions, ticks the review block and saves stage reviewed as version 2.
  • Blocker: the routine currently has only the Google Drive connector attached. Without the Education Tracker connector it cannot read the record at all.

Tests

  • /week/2026-W37 renders exactly the counts judgeWeek returns.
  • A saved review appears with its stamp, stage and time.
  • The drift line appears when the snapshot differs from live, and disappears when it matches.
  • A golden snapshot of the register for one fixed week, as the practice chart already has.
6

Alternatives considered

a · the routine writes the whole report

Claude generates the week's HTML on Friday and the page serves the stored blob.

Rejected. Two runs disagree, and the page goes stale the moment Dad excuses a block — the register would still show Wednesday's Spanish as missed for the rest of the term.

b · narrative in every section

A sentence of Claude's commentary under each panel instead of one margin.

Rejected. It blurs computed and written, which is the one distinction the parent needs in order to trust either half. Caveat everywhere is Caveat nowhere.

c · the email carries the full report

Send the register, the hours and the subject cards as HTML mail.

Rejected. The record has one home and the page has the links. A mail client is a poor place to hold a number that changes on Saturday.

Recommendation: build it as drawn. One page per week at /week/{iso}, one ledger at /weeks, one stored note per week with a snapshot, and a digest email that only links. The whole design rests on one rule — if a number can be computed, it is never written down — and the Caveat is the visible edge of that rule.

Three things to decide now:

  1. The concept. Ledger-and-margin, or something else, before the schema step lands.
  2. The timing. Friday 14:05 draft-before-review, as drawn — Dad reads a written week before the chat, and the review has an agenda. Or Friday 17:00, one version, recorded after the review — simpler, no drift line, no draft state, but nothing to read beforehand.
  3. The split versus the timetable. The skills report hours against a target split (maths 5 · lit 4.5 · lang 3.5 · cs 3.5 · spanish 1.75) that the seeded timetable does not deliver: an odd week plans maths 4.8 · lit 3.3 · lang 1.4 · cs 2.75 · spanish 1.0. This page reads the timetable, because that is what the register judges — but the two need reconciling one way or the other, and that is a term-planner job, not a reporting one.
  4. The margin's reach. Per-subject carry-forward lines and an overall note, as drawn; or the overall note only, with carry-forward folded into Slipped. Per-subject is five more lines a week to write and the thing the tutoring skills actually pick up on Monday.

Not up for decision: no UI anywhere for approving a day off or excusing a block. Those stay in chat, through the MCP tools, with the reason recorded — the page only ever reports them.

Week 2026-W37 is illustrative but plausible: the register runs against the real timetable seed (valid_from 2026-09-07, odd week, so Thursday's deep block is Maths) and the movement, attempts and practice figures follow the real record — A4's demotion on 13 Aug, the Phase 1 exit check 22/25 on 19 Aug, Lang Q5 25 min 0 blanks on 1 Sep, four Spanish runs at 76.8% pooled. Pre-timetable hours in the term ledger and the eight-week coverage sparklines are drawn to shape, not from the record. Everything inside a frame is the live exercise-book design system; outside it is deck chrome.
